# Локальная работа, main и worktree

Основная папка `/Users/user/Projects/CS2results` служит чистым checkout ветки
`main`. Код и документацию меняют в коротких ветках задачи с отдельным worktree.
Одна задача — одна ветка; завершённые worktree убирают после сохранения нужных
материалов и проверки принадлежности незавершённой работы.

Текущий разбор старой основной папки и её уникальных материалов описан отдельно:
[синхронизация локального checkout](local-checkout-reconciliation-2026-10-29.md).
Правила ниже не означают, что этот разбор уже завершён.

## Начало задачи

1. Прочитать [PROJECT_CONTEXT.md](../PROJECT_CONTEXT.md), проверить `git status`,
   абсолютный путь рабочей копии, ветку и HEAD. Убедиться, что выбрана нужная
   рабочая копия и её изменения относятся к этой задаче.
2. Выполнить `git fetch origin` до выбора базы. Новую ветку `codex/<задача>` и
   worktree создавать от полученного `origin/main`; сохранить SHA базы в отчёте
   задачи. Существующую незавершённую задачу продолжать в её ветке, предварительно
   проверив её состояние и актуальную базу.
3. Не добавлять чужие правки в свой diff или коммит. Незавершённую работу оставлять
   с понятным статусом: путь/ветка, что сделано, что осталось и следующий шаг.
   Не называть её завершённой и не переносить молча в основную папку.

## PR, проверки и релиз

- Изменения попадают в `main` через PR и [существующий CI](../.github/workflows/tests.yml).
  Это относится и к короткому PR с документацией после релиза. Для единственного
  владельца проекта отдельный человек-approver не обязателен; проверки CI остаются
  обязательными. Прямой push в `main` и force-push не используются.
- PR, merge, deploy и внешние публикации выполняются только в явно разрешённом
  пользователем объёме. Общий запрос на соответствующий GitHub/release-цикл
  может покрывать его шаги; само описание этого процесса не разрешает новый PR
  или дополнительную выкладку. Ограничения из [AGENTS.md](../AGENTS.md) сохраняются.
- Во время работы запускаются профильные проверки; полный набор — один раз перед
  согласованным релизом. Для локальных правок только документации достаточно
  проверки ссылок и diff; PR всё равно проходит настроенный CI.
- Релиз собирается из проверенного Git SHA согласованного состава в чистом
  checkout. В отчёте различаются SHA runtime-пакета, версия production и более
  поздний SHA документации: документационный merge сам по себе не требует deploy.

## Перед локальными тестами

Чистая Git-папка не подтверждает актуальность её `.venv`. Для локального runtime
используйте Python 3.12 и версии из `requirements.txt`; не обновляйте общую среду
чужой незавершённой задачи. В выбранном окружении выполните `python -m pip check`
и следующую проверку пинов перед разбором предполагаемых ошибок кода:

```bash
python - <<'PY'
import sys
assert sys.version_info[:2] == (3, 12), "Select project Python 3.12 first"
from importlib.metadata import version
from pathlib import Path
checked = 0
for raw in Path("requirements.txt").read_text().splitlines():
    line = raw.strip()
    if not line or line.startswith("#"):
        continue
    package, expected = line.split("==", 1)
    assert version(package) == expected, f"Runtime pin mismatch: {package}"
    checked += 1
print(f"Runtime pins verified: {checked}")
PY
```

## Обновление основной папки после merge

Ответственный за задачу проверяет, что в основной папке выбрана ветка `main` и
`git status --porcelain --untracked-files=normal` не выводит изменений. Затем
обновляет remote и выполняет только fast-forward:

```bash
git -C /Users/user/Projects/CS2results fetch origin
git -C /Users/user/Projects/CS2results merge --ff-only origin/main
git -C /Users/user/Projects/CS2results rev-list --left-right --count HEAD...origin/main
```

Последняя команда должна показать `0 0`. Сам `--ff-only` проверяет историю,
но не заменяет предварительную проверку чистого дерева. Если есть чужие правки,
локальные коммиты или конфликтующая история, обновление останавливается до разбора.
Автоматический stash/pop, reset и force-push для такой синхронизации запрещены.

CI проверяет коммиты на GitHub, но не обновляет локальную основную папку.
Проверка её синхронизации — завершающий шаг ответственного за merge.

## Сохранность связанных рабочих копий

Основной `.git` может быть общим Git-каталогом нескольких worktree. Перед очисткой
проверяются `git worktree list` и `git rev-parse --git-common-dir`. Нельзя удалять,
переименовывать или заменять основную папку новым клоном, пока от неё зависят
связанные рабочие копии. Их сохранение и возможный перенос разбираются отдельно.
Нужные ignored-файлы и локальные артефакты сохраняются вне Git; секреты в коммиты
и публичные отчёты не попадают.
