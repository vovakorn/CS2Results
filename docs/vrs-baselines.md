# Начальные VRS будущих турниров

Релиз разрешён владельцем 31 октября 2026 («Выкладывай»). В production ещё
не выпущено; новый часовой таймер не создан. Проверка PGL выполнена ранее отдельно,
в ветке `codex/pgl-final-check`; его исторический baseline эта задача не восстанавливает.

## Подготовка без анонса

`{"job":"vrs_baselines","dry_run":true}` проверяет готовность снимков.
Обычный `vrs_baselines` сохраняет только данные; не создаёт публичные посты,
claims или delivery outbox. Нужны `ENABLE_VRS=1`, Liquipedia API, приватный
Object Storage и доступ к публичному Valve GitHub. Telegram, PandaScore,
одобрение профиля анонса и owner policy форматов не требуются.

Job использует существующий полный пагинируемый календарь LiquipediaDB:
Tier 1/2, Offline, без qualifier/showmatch/points и непустого status.
Размер или отсутствие подтверждённого призового фонда не мешают сохранению VRS;
денежные ограничения календаря анонсов сохраняются только для анонсов.
Горизонт — сегодня и семь следующих дат по Москве. Это явный охват;
online, более низкие уровни и отсутствующие в API турниры этим job не охватываются.
План анонсов и предупреждения его покрытия остаются дополнительной проверкой
известных будущих событий, а не доказательством полноты внешнего API.

Для каждого события:

1. Точная `pagename` определяет ключ `liquipedia-page:<sha256 UTF-8 pagename>`.
   Сопоставления по похожему названию, стадии или оформлению нет. Различающиеся
   разделители страниц не сливаются после очистки имён Object Storage.
2. Читается `vrs-snapshots/<safe key>/before/initial.json`. Существующий
   валидный снимок повторно используется; новая версия рейтинга его не заменяет.
3. При отсутствии снимка до начала даты события сохраняется текущий официальный
   Valve VRS. За один invocation источник читается максимум один раз для всех
   нуждающихся событий. Conditional create и последующее чтение подтверждают
   фактическую версию, включая победителя параллельной записи.
4. И `effective_at`, и фактический `fetched_at` должны содержать часовой пояс
   и быть строго раньше 00:00 первого дня события по Москве. Время из будущего
   дальше пяти минут от начала invocation отклоняется. На первом дне при
   отсутствии baseline выставляется `missed_start`: поздний снимок не выдаётся
   за before. Консервативная граница не предполагает неизвестное время первого матча.

Если уже записанный baseline не соответствует более ранним исправленным датам
календаря, job сообщает ошибку и не перезаписывает immutable-объект.

## Повторы и наблюдаемость

Отдельный job предназначен для часового таймера. Ошибка источника, хранилища
или неполная запись не помечается успехом: следующий вызов повторяет подготовку,
пока старт ещё впереди. Обычный `preview_discovery` также вызывает подготовку
до проверки флага анонсов и загрузки профилей. Поэтому его существующий ежедневный
таймер остаётся дополнительной попыткой даже при выключенных анонсах/невалидных профилях.
Источник может отсутствовать несколько дней: семь дней горизонта дают время
восстановить доступ до старта; абсолютная гарантия доступности API не предполагается.

В приватном bucket записываются:

- `diagnostics/vrs-baselines/latest.json`: проверенное время, статусы всех событий,
  неполные строки календаря, безопасные типы ошибок;
- `diagnostics/vrs-baselines/events/<baseline_id>.json`: последняя проверка каждого
  события, сохраняющаяся после его выхода из текущего окна.

`saved`, `existing`, `would_capture` означают готовность/проверенный dry-run;
`retry` и `missed_start` требуют внимания. Неполный календарь, ошибка source или
записи отчёта возвращают HTTP 503. Ошибка не теряется под успешным статусом.
Уведомление владельца использует существующий cooldown; последовательные одинаковые
ошибки после сохранённого отчёта повторно не уведомляют. Изменение проблемы или
её повторное появление после успеха снова допускает уведомление. Dry-run не пишет
ни снимки, ни отчёты и не отправляет уведомления.

## Потребление перед финалом

Анонс сначала использует прежний `event:<profile.key>/before/initial`.
При его отсутствии копирует уже сохранённый календарный baseline под этот ключ,
сохраняя исходные версию/даты. Если нет обоих, действует прежний прямой capture.

Финальный VRS сохраняет приоритет прежнего event/legacy baseline. Если его нет,
проверяет календарный `initial` по точному `match.tournament_parent` Liquipedia.
Поэтому смена PandaScore group/playoffs → Liquipedia final не теряет новый before.
Идентификаторы публикаций, Threads, claims, owner policy и данные результата
не меняются. Для VRS-поста по-прежнему обязателен новый after после завершения
и однозначное покрытие всех участников; эта задача не добавляет ожидание after в outbox.

## Включение после согласованного релиза

1. Выпустить main по принятому PR/CI/release-процессу; до него полный pytest,
   затем обычные candidate/startup/source gates.
2. На точном `production` выполнить `{"job":"vrs_baselines","dry_run":true}`.
   Проверить страницы, даты, охват и `would_capture`/`existing` для будущих событий.
3. Вызвать обычный job и прочитать сохранённые immutable baseline и отчёт.
4. Создать **один** private timer `cs2-vrs-baselines`, cron `0 * * * ? *`,
   payload `{"job":"vrs_baselines"}`. Он должен вызывать main с тегом
   `production` через текущий service account. Прежние таймеры не менять;
   ожидаемое число триггеров согласовать с актуальным preflight-снимком.
5. Повтор job должен показать `existing` и сохранить исходные `fetched_at`/версию.
   Проверить ошибки и отсутствие публичных публикаций.

В rollout не входят поздний backfill PGL, релиз других функций или тестовые посты.

новые 25 регрессий, main, identity, preview/calendar, VRS и recovery safety.

поведение при неполном календаре, старт/будущие даты, отсутствие внешних отправок,
совместимость legacy и независимость от анонсов/социальных credentials.
