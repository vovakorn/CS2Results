# Автоматический Reel расписания

`job=schedule_reel` — отдельный от Telegram и обычных Instagram-карточек выпуск.
Он использует тот же PandaScore Tier-1 отбор, что `job=schedule`, и показывает
все 1–20 выбранных матчей по времени МСК. Пустой день пропускается; при 21+
матче выпуск целиком пропускается с диагностикой, без скрытого сокращения.

## Локальное превью

```bash
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/preview_schedule_reels.py
```

Четыре MP4 и первые кадры создаются в `build/reel-previews/` (папка исключена
из Git). Матчи в них вымышленные, каждый кадр отмечен «ДЕМО · НЕ ПУБЛИКОВАТЬ».
Проверить 1, 4, 10 и 20 матчей, русские заголовки (включая Ё/ё), длинные
латинские названия команд, отсутствие
логотипа, светлый/тёмный логотип, звук и отсутствие перекрытий в интерфейсе
телефона. Production-рендер не ставит демо-пометку.

В локальной типографической версии имена используют две строки и кегль
не ниже 36 px; порядок и длительность сцен сохранены. Во всех сценах
логотип центрирован, название CS2 RESULTS размещено непосредственно под ним
с помощью общего с PNG-карточками рендерера бренда. Общая проверка карточек
и сцен описана в [типографической системе](typography.md). Итерация не выпущена.

## Локальная итерация 3 октября — первый матч и анимация

- Intro хранит `featured_match` отдельно от полного списка сцен: ближайшая
  пара и её время видны сразу, но подсчёт и порядок основного списка не меняются.
- Появление четырёх матчей занимает менее 0,75 с; остаток 4/5-секундной страницы
  показывает все пары. Кэшируются два растра страницы, логотипы не скачиваются
  повторно для каждого кадра. Общая полоса прогресса остаётся внутри рамки.
- Анимационные ключевые кадры — 12 fps, итоговый H.264/AAC — 24 fps.
  Длительности 8/8/16/29 с для 1/4/10/20 матчей прежние. Таймер и публикация
  не меняются. Обновлённый рендер не выпущен; до релиза нужен Linux/cloud
  render probe для времени и памяти, локальный MP4 не заменяет эту проверку.
- По выбору пользователя старый мелодический луп заменён оригинальным
  синтезированным битом 150 BPM: kick, бас, snare, хай-хэты и короткие аккордовые
  акценты, без вокала. Четыре такта / 6,4 с повторяются без разрыва; звук
  плавно появляется и затухает за 0,25 с на границах всего видео. Синтез
  использует стандартную библиотеку и фиксированный seed, внешние треки,
  сервисы и новые зависимости не нужны. Запас уровня сохраняется до AAC.
- Логотип канала увеличен только в Reel с 116 до 144 px во всех сценах,
  центр остаётся на уровне линий (y=214), название и основная сетка сохранены.
  Размер 88 px для статических турнирных карточек пока остаётся предложением.

### Две версии музыки для сравнения

- `render_schedule_reel(..., audio_style="esports")` сохраняет энергичный
  вариант 150 BPM и остаётся прежним значением по умолчанию.
- `audio_style="minimal"` выбирает синтезированный минималистичный бит 120 BPM:
  ровный kick, тёплый бас и тихая перкуссия без ведущей мелодии и вокала.
  Петля — четыре такта / 8 с, fade на границах видео тот же. Неизвестное
  значение отклоняется до начала рендера. Production-конфигурация не меняется.
- Обе демоверсии создаются из одних матчей и визуально идентичны:
  `python scripts/preview_visual_refresh.py --output /tmp/reel-two-beats --encode-reel --audio-style both`.
  Получаются `reel-esports.mp4` и `reel-minimal.mp4`; данные и знаки команд тестовые.
  По решению пользователя для будущей ротации оставлены только эти два бита.
  Исходный мелодический звук не используется в новых Reel; доступны только
  `esports` и `minimal`. Job чередует их по сохранённым выпускам, а не датам:
  первый — энергичный, после него минималистичный и обратно. Пустые дни
  не учитываются. Последний контейнер до этой версии, без `audio_style`,
  начинает новую последовательность с энергичного бита. История читается
  постранично из `reels/`; ошибка чтения не сбрасывает последовательность.
  Выбранный `audio_style` сохраняется атомарно вместе с контейнером;
  повтор продолжает существующий контейнер, не меняет музыку и не создаёт видео.
  Очередь учитывает подготовленные контейнеры, включая ещё обрабатываемые:
  не требуется дополнительная запись после внешней публикации.

### Турнирное оформление Reel — локально

- `ReelVisualContext` один раз определяет точные профили всех выбранных матчей,
  через существующие provider ID / `event_for_match`. Единый известный турнир
  получает акцент, свечение, официальный логотип с полупрозрачной копией,
  турнирную шапку на intro/matches/outro и цветную полосу прогресса.
- Смешанный день сохраняет нейтральную общую шапку. Каждый матч получает
  собственные цвет и логотип; intro подписывает турнир ближайшей пары.
  Общий цвет не выбирается по первому матчу или по однородной странице альбома.
- Турниры без точного профиля не получают выдуманную палитру. Для логотипа
  используется локальный файл профиля, затем официальный URL источника,
  затем только название. Совпавшие названия города не разрешают заимствовать
  знак другого события. Загрузка ограничена общим 15-секундным бюджетом;
  официальный знак кэшируется на весь ролик, не скачивается на каждый кадр.
- `ReelScene.context_matches` хранит ссылки на исходный полный список только
  для общей темы; `matches`, хронология, 1–20 матчей и 8/8/16/29 с прежние.
  Конфигурация, таймеры и безопасная доставка не меняются. Ротация двух битов
  подключена; историческое демо с мелодией не является доступным вариантом.
- Превью трёх палитр и смешанного выпуска:
  `python scripts/preview_tournament_reels.py --output /tmp/tournament-reels --counts 1 4 10 20`.
  BLAST/PGL используются из демонстрационного реестра только этим скриптом;
  live-реестр не расширяется. Каждый кадр явно помечен, данные вымышлены.

Ролик — 1080×1920, 24 fps, H.264/AAC; максимум 29 секунд при 20 матчах.
Изображения сцен делает Pillow, FFmpeg берётся из закреплённого
`imageio-ffmpeg` wheel. До включения нужно измерить время рендера, память и
доступность Linux-бинарника в candidate Cloud Function; успешный локальный
прогон на macOS не доказывает готовность облачной среды.

Для candidate smoke без источников данных и без публикации используйте
`{"job":"schedule_reel","dry_run":true,"render_probe":true}`. Он кодирует
временный демонстрационный ролик на 20 матчей с локальным турнирным профилем,
цветом/логотипом/фоновой копией, возвращает время, размер MP4 и
пиковую память процесса (на Linux), но не сохраняет и не загружает видео.

## Подготовленная, но выключенная публикация

- Нужны **оба** флага: существующий `ENABLE_INSTAGRAM_PUBLISHING=1` и новый
  `ENABLE_INSTAGRAM_REELS=1`. По умолчанию второй выключен. При `dry_run=true`
  `job=schedule_reel` возвращает ID матчей, число сцен и длительность без MP4,
  загрузки в Object Storage и запросов к Meta.
- При разрешённом запуске MP4 загружается в существующий public media bucket,
  а ID созданного Meta-контейнера атомарно сохраняется в приватном state bucket
  под `reels/<дата>.json`. Подготовка контейнера не публикует пост.
- Текущий пятиминутный `results` trigger с `retry_only=true` проверяет контейнер
  текущего дня. `IN_PROGRESS` оставляет его на следующий запуск. Только
  `FINISHED` допускает `media_publish`; прямо перед ним отдельный Reel claim
  переходит в неперехватываемый `attempting`. Неоднозначный исход блокирует
  автоматический повтор и требует ручной проверки Instagram.
- `share_to_feed=false` предназначен для вкладки Reels, а обычная карточка
  расписания остаётся в основной сетке. До включения подтвердить этот параметр
  и полный контейнерный цикл именно для текущего Instagram Login, а не только
  по документации Facebook Login.
- Не запускать вчерашний Reel в новый день. Текущий worker проверяет лишь
  контейнер сегодняшней даты.

В production создан отдельный timer trigger на `production` в 06:15 UTC
(09:15 МСК):

```text
15 6 ? * * *
```

```json
{"job":"schedule_reel","source":"pandascore","mode":"production"}
```

Проверка релиза ожидает шесть timer triggers. Сам trigger не разрешает
публикацию без `ENABLE_INSTAGRAM_REELS=1`; включение флага и тестовый пост
требуют отдельного согласования.

## Пилот

После утверждения визуала и выпуска — четыре недели ручного учёта: дата,
охват/просмотры Reel, охват карточки расписания, подписчики Instagram и
Telegram на конец недели, ошибки доставки. Динамика Telegram сама по себе не
доказывает переход именно из Reel.
