Первоначальный порядок ниже сохранён как критерии release-цикла.

1. Сверить финальный diff и зависимости пакетов. Определить, каким Python-функциям
   нужен новый архив: основной бот, админка и использующие изменённые общие
   storage/publishing modules publishers. Для каждого зафиксировать применимые
   изменения, handler, набор файлов и проверки. Одобрение относится к конкретному
   составу выпуска; новая функциональность в него не добавляется.
2. После согласования выпуска один раз выполнить полный набор, штатные проверки
   зависимостей и все требуемые сборки. Зафиксировать Git SHA и hashes пакетов.
   Полный pytest должен пройти все текущие тесты; обнаруженные отказы
   разбирать точечно, сохраняя строгую валидацию и смысл проверок.
3. Один PR → зелёный CI Python 3.11/3.12 и существующие Node-проверки → review →
   merge. Создать candidate для согласованных функций, проверить dry-run,
   startup-логи и необходимые render/source probes. Сохранить конфигурацию,
   приватность, timer tags и rollback. Предыдущее разрешение пропустить логи
   не переносится на новый candidate.
4. Только после успешных проверок продвинуть candidate в production, повторить
   smoke и сверить фактические теги/таймеры. Обновить документы реальными
   версиями и результатами, не объявлять успешную доставку по одному dry-run.

## Проверки первых штатных выпусков после релиза

- Новый schedule/context: журнал содержит отдельные логические выпуски;
  частичный контекст не становится подтверждённым целиком.
- Ожидающий Reel: выключенный или старый generation не обращается к Meta;
  новый разрешённый generation доставляется обычным worker без дубля.
- Журнал при недоступном объекте: ошибка чтения не выглядит как ноль публикаций.
- Реальные UI Telegram/Instagram/Threads: проверить читаемость и отсутствие
  неожиданных полей/обрезки на фактических публикациях.

Старые claims, pending и публикации не удаляются и не повторяются ради этих
проверок. Отдельные внешние тестовые посты возможны только в согласованном объёме.
