# Data Contract

Этот документ фиксирует границу между модулем данных `cs2bot.match_sources` и слоем публикации `cs2bot.main`.

## Ответственность data-layer

`cs2bot.match_sources` отвечает за получение, нормализацию и фильтрацию данных
матчей и турнирного контекста.

Он делает:

- получает завершённые матчи из PandaScore;
- использует LiquipediaDB fallback, если включён `ENABLE_LIQUIPEDIA_FALLBACK`;
- приводит данные к `MatchNormalized`;
- заполняет `start_date`, `end_date`, `date` и `maps`, если источник отдаёт эти поля;
- сохраняет provider-scoped ID лиги, серии, турнира, команд и победителя в
  `source_refs`;
- сохраняет `tournament_tier`, `rescheduled`, `original_scheduled_at` и `forfeit`,
  если PandaScore отдаёт эти поля;
- сохраняет для Liquipedia карты, `best of`, tier и publisher tier, стадию,
  точность даты, VOD и статусы технического результата, если они доступны;
- для явно отмеченного финала сопоставляет победителя с первым местом турнира и
  сохраняет `winner_prize_usd`, только если LiquipediaDB отдал однозначную сумму;
- сохраняет необязательные `team1_logo_url` и `team2_logo_url`, если PandaScore
  отдаёт изображения команд;
- отбрасывает невалидные матчи;
- применяет Tier-1 LAN фильтр;
- логирует свежесть источника через `source_fresh`, `source_stale`, `source_future_timestamp` или `source_freshness_unknown`;
- не возвращает stale/undated данные для production-публикации;
- проверяет дедупликацию, если вызывающий слой просит `check_processed=True`.

Он не делает:

- не отправляет сообщения в Telegram;
- не генерирует карточки;
- не помечает матч обработанным после публикации;
- не знает о конкретных Telegram-каналах, кроме CLI debug-режима с `--channel`.

## TournamentPreview

`TournamentPreview` содержит паспорт Liquipedia (`name`, `start`, `end`,
`prize_pool_usd`, `locations`, `participant_count`), необязательное обогащение
PandaScore (`teams`, `first_match_at`) и проверенные `story`, `stages` со ссылками,
`verified_at`, `fetched_at`, `warnings`. Поля отсутствующих обязательных фактов
не заполняются догадками. `prize_money_usd` и `club_reward_usd` задаются парой
с подтверждающим источником и проверяются по сумме API. Страница турнира и
serie связаны только явно проверенным профилем. Списки команд читаются по всем
стадиям, дедуплицируются по provider ID и допускаются только целиком.
Начальная стадия и плей-офф обязательны; крайние даты проверенного регламента
должны совпадать с диапазоном турнира из API.
`branding` переносит проверенные цвет, имя локального PNG-ресурса, исторический
заголовок и их источники. `stages[].card_summary` содержит короткий проверенный
формат/переход для обложки со ссылкой на регламент стадии. Эти поля оформления
не заменяют паспорт и полный регламент.
`PreviewBranding` дополнительно принимает `theme_key`, `series_key`,
`organizer_key`, `secondary`, `background`, `motif` и `theme_source_urls`.
Неуказанный `accent` нормализуется из выбранной темы или в прежний `#16C7FF`.
Разрешение происходит при валидации профиля/паспорта по отдельному локальному
реестру; явные параметры сохраняются. Все эффективные поля входят в snapshot,
поэтому повтор не зависит от последующего изменения палитры реестра.
Темы не создают профили, не ставят `approved=true`, не меняют provider ID,
preview UID, claims, delivery keys или начальный VRS. Происхождение темы и
редакционная проверка фактов — независимые состояния.
Оформление финала и итогов повторно использует `branding` по точным
provider ID/page того же профиля через `branding_for_match`. Renderer итогов
принимает необязательный keyword `branding`; он применяется ко всем страницам,
не меняет placements, источники или ключи доставки. Без профиля используется
прежнее оформление; недоступный файл логотипа не блокирует таблицу. Реестр
неодобренных демонстрационных примеров автоматически не используется.
В локальной итерации 3 октября VRS получает этот же необязательный `branding`
от handler во всех трёх каналах. Расписание и дайджест разрешают оформление
страницы только при совпадении точного профиля у каждого матча; отсутствие
связи хотя бы у одного или разные розыгрыши сохраняют нейтральный вариант.
Доступный URL логотипа следующего матча не теряется из-за пустого URL первого.
`maps` обычного результата не дополняется: рендер полоски требует 1–5 полных,
нетехнических счётов, совпавших с общим результатом; при известном best_of
число карт и побед также обязано ему соответствовать.
Нормализованные поля, ID, fingerprints и ключи доставки не меняются.
Турнирное оформление Reel использует тот же exact provider join
на всём выбранном списке. `ReelScene.context_matches` — контекст темы и состава intro,
не дополнительный публикуемый список. Неоднородный/неподтверждённый выпуск
не наследует общую тему первого матча; неизвестные события с одинаковой
city/competition-подписью сохраняют отдельные названия и логотипы.
Локальный intro 4 октября больше не содержит `featured_match`; все команды
выводятся из полного `context_matches`, не из первой страницы. Повторы
сворачиваются только по имени без регистра/повторных пробелов, без fuzzy alias
или смешения академии с основной командой. Пустой primary/fallback URL может
дополняться следующим появлением этой команды. При равном старте порядок
плиток стабилен по match ID, без редакционного рейтинга. Это только отображение:
normalized models, matches, content UID, media/state schemas и дедупликация прежние.
`reels/<YYYY-MM-DD>.json` хранит необязательный `audio_style`: только `esports`
или `minimal`. Отсутствие/`null` допустимы для прежних контейнеров, которые
не перерендериваются. Новая запись сохраняет звук атомарно с первым контейнером;
следующий выпуск выбирает противоположный звук последнего предыдущего состояния.
Ошибки истории не приводят к молчаливому сбросу, пустые дни не учитываются.
Короткий слоган `branding.headline` хранится в профиле со ссылкой на проверенный
факт; рендер не создаёт его автоматически и пропускает строку при отсутствии.
ISO-даты в моделях и API сохраняются; в отображении месяцы пишутся словами,
год остаётся в общих датах подписи и в диапазонах через Новый год.
`prize_split_kind` различает доли игроков/клубов и призы/оплату участия:
второй вариант используется для BLAST, без подписи «Игрокам».
Локальный CLI допускает `--draft` для неодобренного профиля, сохраняя лимит
давности проверки и пометку на каждом PNG/в подписи. Production-job не включает
этот режим. Примеры BLAST/PGL лежат отдельно от стандартного реестра публикаций.

Доставка использует `preview_{profile.key}_{channel_id}`; profile key включает
конкретный розыгрыш, не дату запуска. Content type — `tournament_preview`.
Meta UID: `<platform>_tournament_preview_<profile.key>` для Instagram и Threads;
claims и markers независимы. `short_story` — проверенная версия основной истории
на 20–100 символов для Threads, с тем же источником; без основной истории
профиль её не принимает. Полные обязательные факты не сокращаются до лимита.
Профиль хранит точную Liquipedia page, PandaScore serie и проверенные
`pandascore_tournament_ids` стадий. Page, serie и stage ID не могут принадлежать
двум профилям. `event:<profile.key>` — общий ключ VRS; `threads:event:<profile.key>` —
ключ всей цепочки Threads. Сопоставление только по точным provider ID/page,
без похожих названий. Исторические профили сохраняются: истечение редакционной
проверки или снятие approval блокируют новый анонс, но не меняют ключ результатов.
Детали: [`tournament-preview.md`](tournament-preview.md).

## VRS snapshots

VRS берётся из официального репозитория Valve
`ValveSoftware/counter-strike_regional_standings`, из versioned Markdown-файлов
`live/{year}/standings_{region}_{date}.md`, и не смешивается с PandaScore или
Liquipedia. Каждый снимок обязан содержать `source`, стабильную
`version`, `effective_at`, `fetched_at`, а также полный список команд с
`team_id`, очками и местом.

Valve может публиковать несколько разных составов под одним названием. Парсер
сохраняет все строки: при совпадении исходного ID использует стабильный hash
названия/указанных игроков, без даты и места в рейтинге. ID единственных команд
сохраняются для совместимости с уже записанными снимками. Valve может указать
меньше пяти игроков; они сохраняются как в источнике. Повтор того же состава
или отсутствие состава при коллизии отвергается. Если итоговая команда имеет
несколько одноимённых строк в before/after, расчёт блокируется: выбирать
последнюю строку или команду с большим числом очков запрещено.

Baseline сохраняется перед первой доставкой анонса турнира при `ENABLE_VRS=1`.
Для профиля это неизменяемый объект
`vrs-snapshots/event_<profile.key>/before/initial.json`: внутри хранится фактическая версия
Valve. Условный create сохраняет только первый снимок, даже если повторный
запуск получил более новую версию. `effective_at` и `fetched_at` должны быть
раньше московского дня начала турнира. Ошибка получения/сохранения baseline
блокирует анонс до безопасного повтора; dry-run и запуск вне окна его не пишут.
Радар baseline больше не создаёт. After-снимок — после финала: его версия и
`effective_at` должны быть новее baseline и не раньше завершения турнира.
After хранится неизменно в `vrs-snapshots/event_<profile.key>/after/{safe_version}.json`.
Компоненты Object Storage проходят `safe_storage_part`; логический ключ
`event:<profile.key>` в имени объекта содержит `_` вместо `:`.
Для турниров без профиля сохраняется чтение старых versioned baseline.

Если нет версии, даты, baseline, after-снимка или хотя бы одной команды из
подтверждённой итоговой таблицы, VRS-публикация пропускается. Причина
фиксируется статусом `vrs_baseline_unavailable` анонса с алертом или событием
`vrs_publication_skipped` итогового выпуска.

VRS-альбом использует отдельный outbox `content_type=tournament_vrs_standings`
и content UID `tournament-vrs-v1:{channel}:{tournament}`, поэтому не дублирует
обычный альбом итогов турнира.

## Цепочка турнира в Threads

Для турнира из реестра ключ — `threads:event:<profile.key>`: анонс, все стадии
PandaScore и финал Liquipedia используют одну цепочку. Только анонс может создать
её корень; другие посты ждут подтверждённого `root_id`. Если профиль не найден и источник дал
`source_refs.tournament_id`, используется он вместе с `source`; иначе —
`tournament_parent`, затем `competition_key` или название турнира. Имя не
заменяет доступный стабильный ID. Object Storage хранит JSON по ключу
`threads/chains/{sha256(tournament_key)}.json` с неизменным `root_id` анонса,
подтверждённым `tail_id`,
временным `reservation` и признаком `blocked`; секретов в нём нет.

Append резервируется условной записью `If-None-Match` или `If-Match` до запроса
к Threads. Анонс создаёт корневой пост один раз; tail передаётся
в `reply_to_id` single-image или carousel parent container. Новый tail
фиксируется только после ответа с post ID. Неопределённый исход блокирует
цепочку конкретного турнира, определённый отказ снимает reservation. После
ручной сверки фактического post ID оператор восстанавливает tail через
`restore_threads_chain_tail(tournament_key, tail_id)`. Если исход отправки
самого анонса был неопределённым, восстановление требует также проверенного
`root_id`; уже подтверждённый корень заменять нельзя. Старые независимые посты
в состояние цепочки не импортируются. Без профиля действует прежняя цепочка
по источнику: её корнем становится первый пост, межисточниковая связь не угадывается.

## Ответственность delivery-layer

`cs2bot.main` отвечает за Cloud Functions handler и публикацию.

Он делает:

- получает матчи через `get_new_finished_matches(..., check_processed=False)`;
- применяет фильтры каналов по командам;
- атомарно резервирует per-channel доставку через conditional Object Storage write;
- проверяет новые канонические и старые source-specific ключи дедупликации;
- отправляет сообщение в Telegram и, при включённых независимых флагах,
  публикует готовые карточки в Instagram и Threads;
- при включённом `TELEGRAM_MEDIA_CARDS` безопасно загружает логотипы,
  детерминированно генерирует PNG для отдельных результатов, вечернего итога и
  расписания; карточки результатов отправляет со спойлером;
- возвращается к текстовой публикации при определённом отклонении карточки Telegram API; при сетевой ошибке, HTTP 5xx или невалидном ответе исход доставки считается неизвестным и fallback не выполняется;
- после подтверждённой отправки сохраняет в claim состояние `sent`, затем
  помечает конкретный канал или платформу обработанными;
- восстанавливает отсутствующий processed marker по claim со состоянием `sent`, не отправляя сообщение повторно.

## Основной объект

Все источники должны возвращать `MatchNormalized`.

Минимально пригодный матч содержит:

- `team1_name`;
- `team2_name`;
- `score1`;
- `score2`;
- `tournament_name`;
- `match_id` или `match_url`.

`maps` всегда должен быть списком. Если карты неизвестны, используется пустой список.

`team1_logo_url` и `team2_logo_url` не влияют на идентичность матча и не являются
обязательными. Delivery-layer принимает изображения только с разрешённого CDN
PandaScore; URL от других источников не загружаются.

`start_date` и `end_date` хранят исходные ISO datetime от источника. `date` остаётся совместимым полем отображения и обычно равно `end_date`, если оно известно. `competition_key` хранит стабильное название соревнования без названия стадии и используется только для cross-provider дедупликации.

`source_refs` содержит идентификаторы только в пространстве текущего `source`:
`league_id`, `serie_id`, `tournament_id`, `team1_id`, `team2_id` и
`winner_team_id`. Эти значения предназначены для будущих связей с командами,
турнирами и сетками. Они, как и `tournament_tier`, не входят в fingerprint и не
могут создавать повторные публикации при переключении источника.

`is_final`, `winner_prize_usd`, `tournament_parent` и `tournament_placements` —
только source-confirmed поля LiquipediaDB. Итоговая таблица принимается, только
когда в ней есть чётное число участников (не меньше двух), все участники
уникальны и призовые подтверждены для каждого; непарный или частичный ответ не
публикуется. VRS-альбом строится только по тому же полному составу.
Место сохраняется из источника: отдельное `4` не считается бронзовым;
`3`, `3-4` и `3–4` выделяются бронзой. Отсутствие матча за третье место
не угадывается по порядку строк или одинаковым призовым: разделённое место
должно быть явно указано в исходной таблице.
Специальная карточка финала с картами и призовыми создаётся исключительно для
матча с `source=liquipedia`, явным признаком финала, суммой победителя и полным
счётом карт. Для PandaScore и неполных данных используется обычная карточка
результата без догадок.

## Турнирный радар

`TournamentRadar.earliest_match_at` содержит самый ранний доступный `scheduled_at`
или `begin_at` из запроса всех матчей PandaScore для турнира, включая завершённые.
Если дополнительный запрос недоступен, поле остаётся `null`: ручной радар может
использовать остальные данные, а автоматический выпуск пропускается.

`radar_discovery` публикует турнир только если эта дата попадает в следующий
московский календарный день и в сетке есть хотя бы одна подтверждённая пара.
Авторадар использует стабильный content UID
`radar_{tournament_id}_auto_{channel_id}`; ручной `job=radar` сохраняет дневную
дедупликацию, а `test_run_id` добавляется независимо.

## PandaScore tier

PandaScore tier хранится как одно из значений `s`, `a`, `b`, `c`, `d`. Если
сокращённый объект турнира внутри матча не содержит tier, адаптер одним запросом
получает все недостающие турниры через `GET /tournaments` с `filter[id]` и
кеширует результат в пределах тёплого экземпляра функции. Ошибка этого
необязательного запроса не блокирует получение матчей.

Для утреннего расписания tier `s`/`a` участвует в production-отборе вместе с
явно распознанными Tier-1 турнирами, но только после исключений qualifier,
showmatch, academy, youth и junior. Для завершённых результатов tier не заменяет
строгий Tier-1 LAN-фильтр и остаётся диагностическим сигналом. Для сравнения
решений пишутся агрегированные события `pandascore_tier_diagnostics` и
`pandascore_upcoming_tier_diagnostics`; dry-run возвращает tier рядом с
фактическим решением фильтра.

## Tournament radar contract

`TournamentRadar.earliest_match_at` содержит самый ранний подтверждённый
timestamp матча из `GET /tournaments/{id}/matches`, включая уже завершённые
матчи. Поле может быть `null`, если источник не вернул корректную дату; ручной
радар при этом может использовать остальные данные, а автоматический discovery
не публикует такой турнир.

Автоматическая дедупликация использует стабильный ключ:

```text
claims/content_radar_{tournament_id}_auto_{channel_id}.json
processed/content_radar_{tournament_id}_auto_{channel_id}.json
```

Ручной `radar` сохраняет дневной ключ публикации. `test_run_id` добавляет
отдельный тестовый суффикс в обоих режимах.

## Дедупликация

Data-layer может использовать общий ключ:

```text
processed/match_v1_{fingerprint}.json
```

Delivery-layer использует per-channel ключ:

```text
processed/{channel_id}_match_v1_{fingerprint}.json
```

Fingerprint строится из даты, `competition_key` (или отображаемого названия турнира), нормализованных псевдонимов команд и счёта. Он не зависит от source ID и порядка команд. Если даты нет, применяется старый source-specific UID, чтобы не склеивать разные матчи по недостаточным данным.

Принятый редкий риск: две серии одной пары с одинаковым счётом в одном турнире
в один календарный день имеют один fingerprint. Нельзя добавлять `match_id` или
`source_refs.serie_id` без потери межисточниковой дедупликации: эти значения
provider-scoped. При появлении такого кейса нужен source-independent
`match_instance_key`, подтверждённый минимум двумя источниками; до этого случая
он не вводится, чтобы не создавать повторные публикации при fallback.

Перед отправкой создаётся lease:

```text
claims/{channel_id}_match_v1_{fingerprint}.json
```

До claim нормализованный матч сохраняется в durable outbox:

```text
outbox/results/{channel_id}_match_v1_{fingerprint}.json
```

Outbox хранит исходные данные матча, канал, время создания, последнюю попытку и
счётчик попыток. Чтение проходит все страницы prefix, затем глобально выбирает
сначала ещё не обработанные, потом наименее недавно обработанные элементы и
только после этого применяет limit. После processed marker элемент удаляется.

После подтверждённой публикации счёта явного финала с полной
`tournament_placements` создаётся отдельный outbox item
`content_type=tournament_standings`. Он использует стабильный content UID из
канала или социальной платформы и Liquipedia `tournament_parent`, поэтому не
повторяет ни счёт, ни итоговую таблицу. Определённый отказ остаётся в очереди для retry; при
неоднозначном исходе применяется тот же ручной разбор, что и для результата.

`If-None-Match: *` и `If-Match: <etag>` не позволяют двум параллельным invocation одновременно получить один claim. У claim есть состояние доставки в metadata:

- `sending` — короткий lease до внешнего запроса; после истечения
  `DELIVERY_CLAIM_TTL_SECONDS` его можно перехватить;
- `attempting` — непосредственно перед внешним publish-запросом; состояние не
  перехватывается даже после истечения lease, поэтому сбой между запросом и
  фиксацией результата не создаёт автоматический дубль;
- `released` — платформа определённо не приняла запрос, claim можно сразу
  получить заново;
- `uncertain` — внешний исход неизвестен; состояние не перехватывается и требует
  ручной проверки;
- `sent` — платформа подтвердила доставку; claim не перехватывается и служит для
  восстановления отсутствующего processed marker. Его `expires-at` через 24
  часа — диагностическая метка, а не разрешение на повтор или автоматическое
  удаление.

Для результата Telegram PNG делает до двух безопасных попыток при
`ConnectTimeout`, затем в том же invocation выполняется одна отправка текста и
включается временный text-only режим. Если TCP-соединение не установилось и для
текста, claim переводится в `released`, а outbox сохраняется для следующего timer
invocation. При остальных сетевых ошибках, HTTP 5xx или невалидном ответе нельзя
отличить неотправленный запрос от уже принятого. Claim переводится в `uncertain`,
автоматический retry и текстовый fallback запрещены, а outbox результата
удаляется; повтор возможен только вручную после проверки платформы. Старые
`processed/{channel}_{source}_{match_id}.json` продолжают проверяться.
Записи `attempting`, `uncertain` и `sent` повторяются до трёх раз при временной
ошибке Object Storage. Если запись `sent` окончательно не подтверждена, уже
существующее состояние `attempting` остаётся неперехватываемым и не допускает
повторную публикацию.

## Публичные медиа

- Instagram/Threads PNG: `<platform>/<publication_key>/<index>-<sha256>.png`.
- Instagram Reel: `instagram/<publication_key>/reel-<sha256>.mp4`.
- SHA-256 считается по полным байтам файла. Неизменный файл сохраняет URL,
  изменённый получает новый URL и не перезаписывает прежний immutable-объект.
- Адрес медиа не является идентификатором доставки. Content UID, claims,
  processed markers и запрет повторов после `attempting`/`uncertain`/`sent`
  сохраняются независимо от изменения дизайна или адреса файла.
- Уже созданный Reel-контейнер использует прежнее видео. Перед сменой шаблона
  проверяется состояние текущего дня; подтверждённые и неоднозначные отправки
  не сбрасываются и не повторяются ради нового оформления.

## Fallback contract

В режиме `source=auto` порядок такой:

1. PandaScore Fixtures adapter (`source=pandascore`).
2. LiquipediaDB adapter (`source=liquipedia`), если `ENABLE_LIQUIPEDIA_FALLBACK=1`.

Решение о fallback принимается после validation и freshness gate. Источники не объединяются в одном запуске. Явный выбор `pandascore` или `liquipedia` доступен для диагностики.

## Liquipedia shadow contract

`ENABLE_LIQUIPEDIA_SHADOW=1` добавляет fail-open сравнение после успешного ответа
PandaScore. Сопоставление использует дату и нормализованную пару команд, поэтому
порядок соперников у провайдеров не важен. Сравниваются счёт, `best of` и tier;
отдельно измеряется покрытие карт и технических результатов.

Shadow-ответ не объединяется с PandaScore, не участвует в фильтрации,
дедупликации и публикации. Любая ошибка Liquipedia записывается как
`liquipedia_shadow_failed`, после чего основной поток продолжает работу.

`ENABLE_LIQUIPEDIA_FINAL_CARDS=1` дополнительно выбирает полный объект
LiquipediaDB вместо PandaScore только для свежего, явно отмеченного финала с
картами и однозначными призовыми победителя либо полной итоговой таблицей. Это
fail-open правило: при ошибке Liquipedia или неполных данных остаётся обычный
PandaScore-результат.

## Freshness contract

Свежесть источника считается по максимальной дате среди `end_date`, `date`, `start_date`.

Если последний матч старше `MAX_SOURCE_STALENESS_HOURS`, отсутствует дата или timestamp слишком далеко в будущем, production-вызов не получает эти матчи.

```text
event=source_stale
```

Для диагностики stale-ответ можно увидеть только в dry-run при `ALLOW_STALE_IN_DRY_RUN=1`.
