## Рабочая схема дальше

1. Новую задачу начинать от свежего GitHub main в чистой рабочей копии.
2. Изменения делать в отдельной `codex/...` ветке, вместе с тестами и документами.
3. После разрешения на выпуск: PR → успешный CI → merge в GitHub main.
4. Обновить чистую копию main и собрать candidate из точного слитого commit.
5. После smoke и разрешения на production продвинуть **тот же** candidate,
   записать Git SHA/версию, проверить таймеры и сохранить rollback.

Merge в GitHub не обновляет другие локальные папки и не переключает production.
Технически deploy-скрипт может собрать любой чистый checkout: он не навязывает
main. Поэтому источник выпуска проверяется отдельно. Рабочие ветки не являются
«живым сайтом»; production — конкретный проверенный архив с тегом `production`.
Грязную старую папку не сбрасывать, не удалять и не добавлять в общий commit.
Согласие на локальное восстановление не разрешает PR, merge, deploy или пост.
