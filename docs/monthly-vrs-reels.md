  20 команд из мирового топ-20 на последней доступной дате месяца. Это не вся
  таблица VRS и не список приглашённых на Major.
- В шапке: «VRS · ИТОГИ МЕСЯЦА», месяц/год и «МИРОВОЙ РЕЙТИНГ · ТОП-20».
  Подпись начинается: «Изменения VRS по итогам сентября 2026 года.»
  Месяц и год подставляются автоматически, включая переход через Новый год.
- График и правый столбец показывают **реальные мировые места**. Место 44
  не становится местом 20 из-за ограниченной выборки. Очки показаны рядом.
- Сохраняются логотип проекта, градиентная шапка, стабильный Canvas-рендер,

## Данные

LiquipediaDB `vrs_ranking_live`; источник и исходные даты указаны в подписи.
Берётся последний рейтинг **до первого числа** и все доступные рейтинги
внутри месяца. Начальный рейтинг должен быть не старше восьми дней до первого
числа, заключительный — не старше семи дней до конца месяца. При недостаточном
покрытии выпуск останавливается. Пропуски не подменяются вымышленными точками.

Рейтинги проверяются целиком, до выбора топ-20. Используются только явно
сопоставленные шаблоны команд и подтверждённые переходы брендов. Новый неизвестный
шаблон в итоговом топ-20 блокирует выпуск до обновления каталога. Смена ядра
состава разрывает линию; критерий — три общих игрока. Ни квоты Major, ни
производный региональный порядок для этого формата не применяются.

## Планировщик и доставка

Отдельная приватная Python-функция `cs2-monthly-vrs-reels`, entrypoint
`cs2bot.monthly_vrs_reels.handler`, Python 3.12, 512 MB, 600 s, concurrency 1.
Она синхронно вызывает приватный Node-рендер `cs2-vrs-major-reels` только по
тегу `production`; основной `cs2bot.main` и его таймеры не используются.

Начало — **1-го числа в 12:00 МСК за предыдущий месяц**. Один таймер вызывает
worker каждые пять минут в 12:00–15:59 МСК 1–3-го числа: cron
`*/5 9-12 1-3 * ? *` (UTC). Это окно безопасных повторов одного выпуска,
а не расписание новых постов. Payload: `{"job":"monthly_vrs","dry_run":false}`.
Таймер должен вызывать `production`, не `$latest`.

Формат cron и UTC: [документация Yandex Cloud](https://yandex.cloud/ru/docs/functions/concepts/trigger/timer).

`ENABLE_MONTHLY_VRS_REELS=1` и общий `ENABLE_INSTAGRAM_PUBLISHING=1`
обязательны; новый флаг по умолчанию `0`. Ежедневный Reel расписания имеет
отдельный флаг. Проверяется owner policy для `instagram:monthly_vrs_reel`;
при недоступной/неинициализированной policy публикации нет. Старая generation
после выключения формата не возобновляется автоматически. Новая строка реестра
админки появится после выпуска её обновлённой версии; отдельный worker сам
не обновляет действующую админку.

За пределами окна worker не публикует. Явный `month` разрешён только в dry-run:
случайный исторический выпуск и автоматический backfill исключены. После
активации в середине октября первый плановый выпуск — 1 ноября за октябрь,
если источник пройдёт проверку покрытия.

## Состояние и защита от дублей

- Приватный `vrs-monthly/YYYY-MM/sources/<sha>.json` и `renders/world/...`:
  content-addressed исходник, MP4, preview, данные, подпись и manifest.
- `vrs-monthly/prepared/YYYY-MM.json`: первый успешный render receipt и
  generation. Повтор использует тот же MP4, сверяя размер и SHA-256.
- `vrs-monthly/pending/YYYY-MM.json`: первый сохранённый Instagram container ID
  и generation; запись `If-None-Match: *`, чужой контейнер не заменяется.
- Claim/processed UID `instagram_vrs_monthly_world_YYYY-MM`. Публикация
  возможна только после `FINISHED` и повторной проверки owner policy, затем
  `attempting → media_publish → sent → processed`. Неопределённый исход
  блокируется для ручной проверки, новый контейнер вместо него не публикуется.

Для Meta в существующий **public media bucket** копируется только проверенный
MP4; исходники и служебное состояние остаются приватными. Используются текущие
Instagram OAuth и Xray, без копирования токенов в код или параметры таймера.
Повтор обработки Meta продолжает тот же контейнер. Подтверждённая публикация
записывается в общий журнал; ошибка журнала не разрешает повторную отправку.

```bash
VRS_FFMPEG_PATH=/absolute/path/to/ffmpeg node video/vrs-major-race/cloud/preview-monthly.mjs 2026-09 build/vrs-monthly-2026-09
```

Порядок согласованного выпуска:

1. Полные тесты, PR/CI/merge. Linux CI собирает и полностью декодирует
   прежний Americas и новый месячный мировой Reel из упакованного handler.
2. Обновить Node-рендер через его candidate/smoke/promote-процесс до
   проверки publisher, если меняется контракт `job=monthly`.
3. `XRAY_ENABLED=1 python scripts/build_monthly_vrs_function.py` — отдельный
   пакет Python worker с закреплённым Xray. Не выкладывать его в основной бот.
4. Создать приватный candidate нового worker, используя текущий service account,
   private state bucket, public media bucket, `INSTAGRAM_LOCKBOX_SECRET_ID`
   и `VRS_RENDER_FUNCTION_ID`. Перенести только pinned Lockbox references
   `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `XRAY_CONFIG_JSON`. OAuth-секрет
   читается штатно во время работы; секретные payload не извлекаются при deploy.
5. Вызвать candidate с `{"job":"monthly_vrs","dry_run":true}`, затем
   с `"inspect_source":true`: второй запрос проверяет новый Node API,
   покрытие месяца и подпись, не пишет состояние и не вызывает Meta.
   Проверить startup-логи. Исключение из предыдущего релиза не переносится.
6. После разрешения перевести worker на `production`, повторить оба dry-run,
   проверить IAM/приватность и исходные версии/таймеры. При первом неуспешном
   smoke удалить новый production-тег; при обновлении восстановить предыдущий.
7. Создать **один** timer `cs2-monthly-vrs-world` с указанным cron/payload,
   привязкой к worker и `production`. До успешного smoke timer не создаётся.
   Исторических или тестовых постов этот процесс не отправляет.

Старый приватный Major-генератор и три региональных ролика сохраняют свой
период/контракт. Этот формат — отдельный месячный мировой выпуск.
