## Что нужно исправить перед выпуском

### R01 · P2 · Старый Reel отправляется после выключения и включения формата

**Места:** `cs2bot/reel_delivery.py:22–27`, `:121–140`, `:151–176`;
`cs2bot/main.py:3378–3385` и `:2571–2579`.

`PendingReel` не сохраняет generation. Worker проверяет только текущее `enabled`.
Воспроизведён обычный последовательный сценарий:

1. Контейнер сохранён и находится в IN_PROGRESS при generation=0.
2. Владелец выключает формат: generation=1, worker действительно удерживает Reel.
3. Контейнер готов; владелец включает формат.
4. Worker публикует тот же старый контейнер, хотя по контракту старая очередь
   должна оставаться удержанной после повторного включения.

Proof использует реальные `_retry_reel_worker`, `update_policy` и state transitions,
FakeS3 и запрет реальных HTTP-запросов. Это не гонка двух потоков: шаги последовательны.
Срабатывание доказано при указанных условиях; частота таких действий владельца
в production не измерялась.

**Минимальное предложение:** сохранить generation в pending Reel и передавать
актуальное поколение в existing advance-путь; старые записи читать с default=0,
как result outbox. Добавить проверки pause → reenable и старого контейнера.
Цена — одно совместимое поле и несколько мест передачи/сравнения, без нового
сервиса, состояния или нечёткого сопоставления. Новых внешних публикаций для
проверки этого исправления не требуется.

### R02 · P2 · Ошибка чтения журнала выглядит как отсутствие публикаций

**Место:** `cs2bot/publication_admin.py:217–219`.

После успешного LIST вызов GET конкретной записи может вернуть 403 или 503.
`read_item` подавляет любой ClientError и возвращает None. Обзор получает пустой
список и показывает «Подтверждённые публикации: 0», без ошибки или оговорки.
При отказе части GET получается столь же незаметное занижение счётчика.

Воспроизведено через реальный boto3 client и botocore Stubber для обоих HTTP-статусов.
Это достижимо при ошибке доступа к отдельным объектам или сбое GET после успешного
чтения policy/LIST; полная недоступность всех S3-операций не требуется.
Частота таких отказов по live-логам не устанавливалась.

**Минимальное предложение:** пропускать только 404, остальные ClientError
превращать в существующий StorageUnavailableError. Админка уже умеет обрабатывать
ошибку данных. Цена — небольшая правка обработки ошибок и две регрессии; чтений
и новых механизмов восстановления не добавляется.

### R03 · P2 · Успешный контекст расписания отсутствует в журнале

**Место:** `cs2bot/main.py:2425–2511`.

`schedule_context` объявлен независимым форматом в админке, но его отправка не
вызывает `_record_post_analytics`/`record_publication`. Proof прошёл настоящую
owner policy generation=1 и существующий Telegram transport с подставленным
успешным HTTP-ответом: один sendMessage, ноль записей в journal wrapper.
Это воспроизводится на успешном пути каждого такого выпуска, а не только при
сетевой ошибке; дефект остаётся после исправления standings/VRS в F09.

**Минимальное предложение:** best-effort запись одного логического выпуска
после подтверждения необходимых частей контекста. Для частичной или неопределённой
доставки нельзя записывать полный успех. Цена — учёт результата уже выполняемых
отправок, одна запись и несколько тестов на текст/обложку/частичный отказ.
Новые claims, повторы и персистентные состояния для этого не нужны.

### R04 · P3 · Пересборка ZIP сохраняет старые entries

**Место:** `scripts/build_social_publish_zip.sh:34–36`.

`zip -qr OUTPUT_PATH ...` обновляет существующий архив. Исключение `-x '*.pyc'`
не удаляет pyc, уже находящиеся внутри него. Воспроизведена обычная цепочка:
импорт Python создаёт `__pycache__`, прежний builder из `b363ac0` собирает ZIP,
текущий builder пересобирает тот же OUTPUT_PATH. Старые три pyc остаются.
Чистая сборка, как в текущем archive smoke, эту ошибку не обнаруживает.

Это дефект воспроизводимости состава пакета. В proof не требовалось добавлять
искусственный основной handler или обращаться к облаку. Аналогичный update-паттерн
виден в небольших admin/OAuth builders; main builder сначала удаляет прежний ZIP.

**Минимальное предложение:** создавать новый ZIP в уже существующем BUILD_DIR
и переносить готовый файл в OUTPUT_PATH. Цена — несколько shell-строк и один
тест пересборки поверх архива со старыми файлами, без новой системы сборки.

### R05 · Проверки выпуска · Не все fixtures финала приведены к новому контракту

**Место:** `tests/test_final_branding.py:11–17`.

Четыре теста падают: параметрические `test_red_brand_keeps_portrait_card_and_both_red_header_segments`
для 4/5 карт, `test_missing_logo_keeps_brand_and_render_usable` и
`test_final_and_all_standings_pages_add_tournament_watermark`.

Fixture сообщает серию 3:1 или 3:2, но все 4/5 карт выиграны одной стороной.
Новая общая проверка правильно отвергает эти данные. Файл не входил в прежние
894 проверки. Дополнительный прогон трёх смежных файлов дал **4 failed, 93 passed**.

**Минимальное предложение:** исправить счета проигранных карт в fixture,
сохранив проверки брендинга и строгую валидацию. Временная копия только с этой
правкой прошла все **11 тестов** файла; исходный файл не изменялся.
Цена — исправление тестовых данных, без изменения поведения продукта.
