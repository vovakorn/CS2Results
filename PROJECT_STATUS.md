# CS2 Results Bot — production-состояние

Обновлено: 1 сентября 2026 года.

Этот файл содержит подробный operational snapshot. Для обычной задачи достаточно
`PROJECT_CONTEXT.md`; этот документ нужен для релиза, инфраструктуры, диагностики
production и сверки фактического состояния. Текущий commit всегда проверяется
через Git и здесь не дублируется.

## Расписание jobs

- `results` — каждые 15 минут.
- `results retry_only` — каждые 5 минут, без запроса источников матчей.
- `schedule` — ежедневно в 10:00 по Москве.
- `digest` — ежедневно в 23:00 по Москве.
- `radar_discovery` — ежедневно в 12:00 по Москве; выбирает Tier-1 турниры
  следующего дня и публикует только при подтверждённых парах сетки.
- `radar` — ручной выпуск выбранного турнира.
- `analytics` — ручные или специально настроенные операции аналитики.

Пустые выпуски не публикуются. Подробные продуктовые правила находятся в
`docs/requirements.md`.

## Источники

- PandaScore — основной production-источник завершённых и предстоящих матчей.
- PandaScore tournament tier собирается для shadow-диагностики и пока не меняет
  production-фильтр.
- LiquipediaDB подключена для fail-open shadow-сравнения; production fallback
  остаётся выключен до решения по итогам наблюдений.
- HLTV и BO3.gg изолированы в `match_sources.legacy`: они сохранены только для
  миграционных тестов и диагностики и не входят в production-пакет источников.
- Источники не смешиваются внутри одной выдачи.

## Хранилище и безопасность

- Токены и ключи находятся в Yandex Lockbox.
- Cloud Function не должна быть публичной.
- Object Storage хранит claims, processed markers и analytics journal.
- Durable outbox хранит нормализованный результат до подтверждённой доставки;
  очередь отдаёт приоритет ещё не обработанным и наименее недавно
  обрабатывавшимся элементам.
- Per-channel claim создаётся атомарно; после подтверждённой Telegram-доставки он
  фиксируется как `sent`, затем создаётся processed marker. Если запись marker
  прервана, следующий запуск восстанавливает его без повтора сообщения.
- Истёкшие claims можно безопасно перехватывать; ETag сравнивается совместимо с
  S3-реализациями, возвращающими значение без кавычек.
- Пользовательские metadata Object Storage читаются регистронезависимо, поскольку
  Yandex может возвращать `Delivery-State` и `Expires-At` с изменённым регистром.
- Перед релизом 1 сентября реальный bucket подтвердил conditional-write
  семантику: из десяти параллельных `If-None-Match: *` claim успешен ровно один,
  а повторная запись со старым ETag отклоняется.
- Cross-provider fingerprint защищает от дублей при переключении источников.
- Критические ошибки отправляются администратору с cooldown; приватный chat ID не
  документируется.
- Внешние логотипы ограничены разрешёнными HTTPS-хостами, типом, размером,
  разрешением, timeout и redirects.

## Проверенные возможности

- Tier-1 фильтрация по турнирам, стадиям, командам и исключениям из
  `tier1_filter.json`.
- Расписание, результаты и вечерний итог с Telegram-спойлерами.
- Карточки результатов на 1–10 матчей и расписания на 1–20 матчей.
- Две хронологические страницы расписания на 11–20 матчей, отправляемые альбомом.
- Официальные логотипы PandaScore, placeholder с инициалами и контрастные
  подложки.
- Текстовый fallback при определённом отклонении карточки Telegram API; при
  неизвестном исходе доставки повтор и fallback не выполняются, чтобы не создать дубль.
- `ConnectTimeout` до установления TCP-соединения считается определённым отказом:
  для результата выполняется одна попытка по 10 секунд за invocation, после чего
  claim освобождается, а outbox повторяется отдельным пятиминутным trigger.
- После photo `ConnectTimeout` результаты на один час переходят в text-only режим,
  чтобы загрузка PNG не расходовала бюджет остальных публикаций.
- Контекст приоритетных матчей: форма, размеры составов и подтверждённые очные
  встречи без прогноза.
- Турнирный радар: до 24 подтверждённых пар PandaScore, по четыре пары на
  квадратную PNG-карточку с нумерацией страниц; таблица положения не публикуется.
- Radar discovery и один контролируемый тестовый пост карточек сетки успешно
  доставлены; dry-run без подтверждённых пар корректно не создаёт публикацию.
- Analytics journal для событий публикаций, снимков подписчиков, invite links и
  ручного импорта метрик.
- Отдельный OAuth handler для Instagram и Threads развёрнут в production как
  функция `cs2-social-oauth`, версия `d4es90gretnlskkega7g`. Запросы к Meta идут
  через Xray-конфиг из Lockbox, отдельный от Telegram proxy; запросы к Yandex
  Lockbox остаются прямыми. Threads OAuth завершён и создал активную версию
  Lockbox; Threads `USER_ID` закреплён в функции как
  `THREADS_EXPECTED_USER_ID` для проверки deauthorize и data-deletion callbacks.
  Для Instagram аналогичный expected user ID остаётся отдельной задачей.
- Telegram-прокси подключён отдельным Lockbox-секретом к основной production-функции;
  dry-run, запрос `getChatMemberCount` и один изолированный тестовый PNG-пост
  выполнены успешно.
- Instagram publishing включён в production 30 августа 2026: основная функция
  использует Xray из Lockbox, OAuth-токен из отдельного Lockbox-секрета и
  публичный bucket `cs2results-instagram-media` только для карточек. Расписание
  и digest имеют отдельные content-claims, результаты — отдельный durable
  outbox-канал `instagram`; Telegram proxy и его доставка не изменялись.
- Threads publisher с отдельными content-claims и durable outbox-каналом
  `threads` развёрнут в основной production-функции 31 августа 2026, версия
  `d4e6r3is9gugc6j6t2jt`, но выключен `ENABLE_THREADS_PUBLISHING=0`. Production
  dry-run завершился `200`; реальных Threads-постов этот релиз не создавал.
  Пользователь включил нативный Instagram → Threads cross-posting для одинаковых
  карточек; его работу с Instagram Graph API нужно подтвердить ближайшим штатным
  Instagram-выпуском. Неуспешный приватный Instagram test invocation (`502`) не
  повторялся, чтобы исключить дубль.
- Локально подготовлено и протестировано увеличение повторов результата при
  `ConnectTimeout` с одной до двух попыток; оно ещё не развёрнуто в production.
- Deploy-скрипт копирует environment variables и Lockbox bindings из production,
  выполняет candidate dry-run и только затем переключает тег.

## Известные ограничения

- PandaScore может не предоставлять полную статистику карт и игроков.
- Liquipedia fallback не активирован до завершения shadow-проверки.
- Классификация Tier-1 зависит от поддерживаемого конфига турниров и стадий.
- Расписание ограничено двадцатью матчами и двумя карточками.
- PandaScore может не опубликовать сетку до старта турнира; в этом случае
  автоматический радар намеренно не выходит.
- Полноценная аналитика источников подписчиков ещё не настроена.

## Безопасный release-процесс

1. Проверить итоговый diff и отсутствие секретов.
2. Запустить полный набор тестов один раз.
3. Создать один PR и дождаться CI.
4. После явного разрешения пользователя выполнить merge.
5. Запустить `scripts/deploy_yandex_function.sh check`.
6. Выполнить один deploy, candidate dry-run и переключение production-тега.
7. Провести один контролируемый тестовый пост, только если он нужен.
8. Обновить этот файл и `PROJECT_CONTEXT.md`, если production-состояние изменилось.

Команды и подробности: `docs/yandex-cloud-deploy.md`. Актуальная продуктовая
очередь: `BACKLOG.md`.
