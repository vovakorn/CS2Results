# Инструкции для Codex

## Начало задачи

- Сначала прочитай `PROJECT_CONTEXT.md` и проверь `git status`.
- Зафиксируй абсолютный путь рабочей копии, текущую ветку/HEAD и SHA базы задачи.
- Перед выбором базы выполни `git fetch origin`. Новую задачу начинай в отдельной
  короткой ветке/worktree от свежего `origin/main`, по одной задаче на ветку.
- Не загружай всю документацию заранее. Открывай только нужный источник:
  - продуктовые правила — `docs/requirements.md`;
  - устройство системы или изменения между модулями — `docs/architecture.md`;
  - модели данных и дедупликация — `docs/data-contract.md`;
  - запуск и конфигурация — `README.md`;
  - production, релиз или инфраструктура — `PROJECT_STATUS.md` и
    `docs/yandex-cloud-deploy.md`;
  - будущие задачи — `BACKLOG.md`;
  - прежняя история — `PROJECT_HISTORY.md`, только по конкретному вопросу;
    не загружай её при обычном старте задачи.
- Не изменяй и не добавляй в коммиты чужие или незавершённые изменения.
- Никогда не добавляй в репозиторий токены, пароли, API-ключи и содержимое
  секретов.

## Основная папка и worktree

- Основная папка `/Users/user/Projects/CS2results` должна содержать чистый `main`.
  Изменения, включая документацию, выполняй в ветке задачи.
- После merge ответственный за задачу обновляет основную папку только при чистом
  дереве и через fast-forward; затем проверяет совпадение HEAD с `origin/main`.
  При чужих правках или расхождении истории остановись: не применяй автоматический
  stash, reset или force-push.
- Не удаляй и не заменяй общий `.git` основной папки: он обслуживает связанные
  worktree. Перед очисткой проверяй `git worktree list`; незавершённые задачи и их
  материалы сохраняй с явным статусом и следующим шагом.
- Порядок работы, CI и обновления основной папки: `docs/local-workflow.md`.

## Экономный режим

- Пиши короткие отчёты: результат, существенная проблема и следующий необходимый
  шаг.
- Не пересказывай документы и не выводи длинные логи или большие фрагменты файлов.
- Сначала используй поиск и точечное чтение, затем открывай только релевантные
  участки кода.
- Объединяй связанные изменения в одну локальную итерацию.
- Во время итерации запускай точечные тесты; полный набор — один раз перед
  согласованным релизом.
- Для изменений только документации проверь ссылки, форматирование и итоговый diff;
  тесты кода не нужны.
- Не обращайся к GitHub, Yandex Cloud и Telegram для каждой мелкой правки.

## Документация после каждой задачи

- Перед завершением каждой задачи проверь, какие продуктовые правила, контракты,
  рабочие процессы и сведения о production изменились. Обнови соответствующие
  документы в той же итерации, до итогового ответа; документация — часть
  готового результата, а не отдельная задача после релиза.
- При изменении поведения обновляй профильный источник из карты выше. Если
  изменились текущее состояние, выполненная работа или очередь задач, также
  актуализируй `PROJECT_CONTEXT.md`, `PROJECT_STATUS.md` и `BACKLOG.md` по их
  назначению. После релиза зафиксируй фактические версию, проверки и риски.
- Для задач без новых устойчивых фактов проверь актуальность документации и
  укажи в отчёте, что правки не потребовались. Не добавляй формальные записи
  ради самого факта изменения файла и не перезаписывай чужие незавершённые правки.

## Локальная работа и публикация

- По умолчанию изменения остаются локальными.
- Без явного разрешения пользователя не создавай PR, не сливай ветки, не выполняй
  deploy и не отправляй сообщения в Telegram.
- Фраза «Утверждаю — выкладывай» разрешает один общий release-цикл для уже
  согласованных изменений: итоговый diff → полный набор тестов → один PR → CI →
  merge → один deploy → dry-run → один тестовый пост, если он нужен.
- Если пользователь просит только GitHub, облако или Telegram, выполняй только
  названную часть.
- После значимого релиза сверь фактическое состояние с документацией и дополни
  обновления, сделанные в ходе задачи.
- Собирай релиз из проверенного Git SHA согласованного состава. Изменения main,
  включая отдельную документацию после релиза, проводи через PR и существующий CI;
  для solo-owner отдельный человек-approver не обязателен. Эти правила сами по себе
  не разрешают новый PR, merge или deploy сверх явно согласованного запроса.

## Проверки

- Точечные тесты карточек: `python -m pytest tests/test_media_cards.py -q`.
- Полная проверка: `python -m pytest -q`.
- Сборка функции: `scripts/build_function_zip.sh`.
- Перед production-деплоем выполни проверку из
  `docs/yandex-cloud-deploy.md`; таймеры должны вызывать тег `production`, а не
  `$latest`.
- Для визуальных изменений проверь варианты на 1, 4 и 10 матчей, длинные названия,
  отсутствующие и контрастные логотипы, отсутствие перекрытий и статичный формат
  1080 × 1350; для Reels — 1080 × 1920 и safe zones.
